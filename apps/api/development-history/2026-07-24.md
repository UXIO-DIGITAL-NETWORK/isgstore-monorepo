## Latest Feature Work

### Monetapay Disbursement Hardening (July 22–24)

The last sprint focused entirely on making the payout side of Monetapay production-safe. Monetapay uses separate credentials for collection (inbound payments) and disbursement (outbound transfers) — these were previously conflated under a single `app_id`. The work involved:

- **Splitting disbursement credentials** from collection credentials — `app_id` and `mch_id` are now distinct per flow, preventing cross-contamination of API contexts
- **Validation layer** — added required-field checks and numeric type enforcement on all disbursement payloads before they leave the server; prevents malformed requests from reaching the Monetapay API and causing opaque failures
- **Logging isolation** — introduced separate Laravel logging channels for Digiflazz and Monetapay so that third-party traffic can be tailed or searched independently without wading through application logs

Before the disbursement sprint, a separate channel (`logging`) was added to give each integration its own traceable log stream.

## Key Decisions Made

**1. Separate `app_id` per Monetapay flow**
Collection and disbursement are different Monetapay "apps" with different credentials. Keeping them unified caused credential mismatches in payout requests. They are now resolved from different env keys.

**2. Action-Oriented architecture (non-negotiable)**
Every business operation is a single-responsibility `Action` class. Controllers only map request → DTO → Action → response. This makes the transaction state machine and refund logic independently testable without bootstrapping HTTP.

**3. In-memory SQLite for all tests**
No test database setup required. Feature tests run in-memory SQLite; the test suite can run on a clean checkout with zero DB provisioning.

**4. Async queue for Digiflazz orders**
Digiflazz fulfillment is dispatched to a queue job, not processed inline. This keeps checkout response times fast and lets the queue retry on transient Digiflazz failures without user-facing impact.

**5. Idempotent refunds via atomic cache**
Refund and duplicate-submit protection is enforced with an atomic cache lock keyed on transaction ID. Double-taps on the same transaction are rejected before hitting the payment gateway.

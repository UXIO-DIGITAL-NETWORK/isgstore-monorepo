Architecture Overview

👤

User / Client

Initiates checkout. Completes payment via QRIS scan or VA transfer. Supports both authenticated and guest flows.

⚙️

Laravel 11 Backend

Strict pipeline: Route → FormRequest → Controller → Action → ApiResponse. All business logic isolated in Actions. DTOs bridge Controller ↔ Action.

💳

Monetapay

Pay-in gateway for QRIS, Virtual Account, E-Wallet. Payloads are AES-128-CBC encrypted. Signatures use Double MD5 with custom delimiters.

🎮

Digiflazz

Product supplier for game top-up, pulsa, PPOB. MD5-signed outbound requests. HMAC-SHA1 authenticates inbound webhooks via X-Hub-Signature.

Mandatory Request Pipeline (no exceptions)

Route → FormRequest (validation) → Controller (maps DTO) → Action (business logic + DB::transaction) → ApiResponse

Exception: CheckoutController validates inline (not via FormRequest) because guest_contact validation is dynamic — required for guests, nullable for authenticated users.

Phase-by-Phase Breakdown

Phase 1

Checkout & Payment Initialization

POST /v1/checkout

Execution Steps

  1. Resolves User (nullable for guests), Product (with active SupplierProducts eager-loaded), and PaymentChannel.
  2. Role-based price resolution: vip → reseller → agent → member → guest. Guests receive price_member.
  3. Margin guard: aborts 400 if selling_price − supplier_price < 0.
  4. Creates Transaction (PENDING) and Payment (status: '1') inside a single DB::transaction().
  5. Calls MonetapayService::createTransaction() — routes to /v1.0.0/qris or /v1.0.0/virtual_account based on payment_type on PaymentChannel.
  6. Returns qr_string or virtual_account to the client for display.

Key Files

Http/Controllers/CheckoutController.php
Actions/Checkout/CheckoutAction.php
Services/Payment/MonetapayService.php
DTOs/Checkout/CheckoutDTO.php

Balance Payment — Special Path

If channel_code === 'balance', Monetapay is bypassed entirely. The user's balance is deducted, Payment is set to status '3', and ProcessDigiflazzTransactionAction is called synchronously (no queue).

Phase 3

Monetapay Webhook Callback

POST /v1/payment/callback

Execution Steps

  1. Decodes payload, verifies Double MD5 HMAC: md5(md5(TOKEN + "*|*" + sortedParams + "@!@" + ts)) using hash_equals().
  2. Anti-fraud: gross_amount from DB must exactly match dto.amount. Throws on mismatch.
  3. Fetches Payment row with lockForUpdate() to block concurrent webhook replays.
  4. Idempotency guard: returns HTTP 200 without re-processing if status ∈ {PAID, PROCESSING, COMPLETED}.
  5. Success signals accepted: "1" (VA/Paid), "3" (QRIS/Settled), "success" (legacy). Evaluated via in_array(strtolower($status), ['1','3','success']).
  6. Updates payments.status = '3' and transactions.status = PAID.
  7. Dispatches ProcessDigiflazzTopup job after the DB::transaction() block returns.

Key Files

Actions/Payment/HandleMonetapayCallbackAction.php
DTOs/Payment/MonetapayCallbackDTO.php
Services/Payment/MonetapayService.php
Jobs/ProcessDigiflazzTopup.php

Critical — Job Dispatch Timing

ProcessDigiflazzTopup::dispatch() is called outside the DB::transaction() closure. This prevents a race condition where a queue worker picks up the job before the Payment/Transaction rows are committed and visible. $transaction->fresh() is called before dispatch.

Phase 4

Digiflazz Fulfillment — Queue Job

ProcessDigiflazzTopup.php

Execution Steps

  1. Sets transactions.status = PROCESSING.
  2. Calls ProcessDigiflazzTransactionAction::execute(Transaction).
  3. Builds Digiflazz payload — key fields: customer_no = target_uid . target_server (concatenated, no separator), ref_id = invoice_number.
  4. Signs request: md5(username + key + ref_id).
  5. Parses sync response: Sukses → COMPLETED, Gagal → FAILED_PROVIDER, Pending → PROCESSING (await webhook).
  6. On infrastructure exception: marks FAILED_PROVIDER, re-throws so the queue can retry.

Key Files

Jobs/ProcessDigiflazzTopup.php
Actions/Digiflazz/ProcessDigiflazzTransactionAction.php
Services/Digiflazz/DigiflazzService.php

Job Retry Configuration

  • $tries = 3 — max 3 attempts
  • $backoff = 30 seconds between retries
  • Queue driver: database in production, sync in tests
Phase 5

Digiflazz Async Webhook

(Optional — only if Phase 4 returned Pending) POST /v1/digiflazz/callback

Execution Steps

  1. Triggered by Digiflazz only when Phase 4 sync response was Pending.
  2. Verifies HMAC-SHA1 on raw request body against X-Hub-Signature header using DIGIFLAZZ_WEBHOOK_SECRET.
  3. Updates Transaction to COMPLETED or FAILED_PROVIDER based on webhook payload.
  4. Sends Discord embed notification on every status transition.
  5. Discord step is silently skipped if DISCORD_WEBHOOK_LOG_URL is not configured — safe to omit in dev.

Key Files

Actions/Log/HandleDigiflazzWebhookAction.php
Http/Controllers/DigiflazzWebhookController.php

Route is Public — No Sanctum Auth

Security relies entirely on HMAC-SHA1 signature verification. This is intentional — Digiflazz cannot send auth tokens. The DIGIFLAZZ_WEBHOOK_SECRET must be kept private and rotated if compromised.

Pending Loop (Phase 4 → Phase 5)

If Digiflazz responds Pending, the Transaction stays at PROCESSING. No retry is queued. The Transaction remains in PROCESSING until Digiflazz sends its own async webhook (POST /v1/digiflazz/callback), which transitions it to COMPLETED or FAILED_PROVIDER.

FAILED_PROVIDER → Auto-Refund

When a transaction hits FAILED_PROVIDER and the original payment was via the balance channel, the user's balance is automatically refunded. External payment channels (Monetapay) do not auto-refund — those require a manual or provider-initiated reverse.

Technical Notes & Invariants

1

Monetapay Cryptography

  • Cipher: AES-128-CBC. Key and IV padded to 16 bytes with \0 null bytes — never "0" character.
  • Signature: md5(md5(TOKEN + "*|*" + sortedParams + "@!@" + ts))
  • Inbound callbacks verified with hash_equals() to prevent timing attacks.
  • Do NOT alter cryptography in MonetapayService — stabilized against official PHP SDK.
2

Job Dispatch After Commit

  • ProcessDigiflazzTopup::dispatch() is always called outside DB::transaction().
  • Prevents race: worker picks up job before Payment/Transaction rows are committed.
  • $transaction->fresh() is called to ensure the dispatched model reflects the latest committed state.
  • The captured $paidTransaction variable bridges the closure to the outer dispatch call.
3

Idempotency & Replay Safety

  • Monetapay may retry the same webhook multiple times.
  • Guard: if transaction.status ∈ {PAID, PROCESSING, COMPLETED}, return HTTP 200 with no side effects.
  • lockForUpdate() on the Payment row blocks concurrent execution of the same webhook.
4

Digiflazz Specifics

  • Signature: md5(username + key + ref_id)
  • customer_no = target_uid . target_server — concatenated, no separator.
  • invoice_number is used as the Digiflazz ref_id.
  • Inbound webhook: HMAC-SHA1 on raw body verified against X-Hub-Signature.
5

Database Key Relationships

  • transactions.user_id is nullable — guest checkouts are supported.
  • transactions.guest_contact stores WhatsApp/phone number for guests.
  • supplier_products.is_active gates availability — only the first active record per product is used.
  • $adminFee = 0 hardcoded in CheckoutAction. Extend there when fee logic is needed.
6

Architecture Invariants

  • Controllers: pure routers — validate, build DTO, call one Action, return response. No DB calls, no conditionals.
  • Actions: own all logic. One Action = one task. State changes run inside DB::transaction().
  • DTOs: readonly PHP 8.2+ value objects — the only thing passed between Controller and Action.
  • Exception: CheckoutController validates inline (dynamic guest_contact rule).

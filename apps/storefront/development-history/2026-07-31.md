# Project Brief — web-topup-fe

**Stack:** React 19 · TypeScript · Vite 7 · TanStack Router v1 · TanStack Query v5 · HeroUI v3 · Tailwind CSS v4 · Zustand v5 · react-i18next
**Role in platform:** Customer-facing SPA — public top-up storefront with guest checkout and member dashboard

---

## Status as of July 31, 2026

Live against the real backend API. Both the storefront and the authenticated member area now read from `web-topup-api` endpoints instead of mock data. A test runner was added in the same milestone. The platform is in production integration — the prototype layer has been retired.

## Latest Feature Work

### Real API Migration + CMS/Wallet/Promo Integration (July 31)

Two PRs landed back-to-back on July 31, completing the transition from mock to live data.

**PR #1 — `feat/api-integration`** (`feat: run the storefront on the real API instead of mock data`)

The storefront had been running on typed mock fixtures to allow UI development to proceed before the backend was ready. This PR swapped every service call to point at real `web-topup-api` endpoints. The service boundary was designed from the start to make this a one-file-per-service change — no component logic changed, only the data layer.

**PR #2 — `feat/cms-wallet-and-promo`** (`feat(storefront): read CMS, wallet and membership from the API; add a test runner`)

With the core checkout wired up, this PR extended live API consumption to three additional data domains:

- **CMS content** — banners, announcements, promotional copy that the storefront renders are now fetched from API endpoints rather than hardcoded
- **Wallet** — authenticated users' wallet balance is read from the backend and displayed in the member dashboard
- **Membership** — member tier and status are pulled from the API, enabling gated UI states (VIP-only prices, member-only features)

A test runner was also introduced in this PR, establishing the testing harness for future coverage.

## Key Decisions Made

**1. Mock-first, API-swap architecture**
The storefront was built against typed mock fixtures behind a stable service interface. Swapping to real API was a mechanical change — service files updated, no component surgery. This let UI development run in parallel with backend development.

**2. HeroUI v3 (not shadcn)**
The customer SPA uses HeroUI as its component primitive layer. This gives a more expressive, themed component set suited to the e-sports premium aesthetic (neon violet, glassmorphism cards, gradient prices). Admin SPA uses shadcn/ui with a monochrome palette — deliberately different.

**3. Tailwind v4 via `@theme` only**
No `tailwind.config.ts` file exists. All design tokens (colors, fonts, radii, spacing overrides) live in `src/index.css` under `@theme`. This makes the design system portable and co-located with the stylesheet.

**4. URL-based locale routing**
Multi-locale is implemented as `/{locale}/...` URL segments, not via cookie or query param. This makes locale-aware pages shareable and crawlable. Default locale is Indonesian (`id`); English (`en`) is the second supported locale.

**5. Zustand auth token in cookie (not localStorage)**
`useAuthStore` persists the access token in an httpOnly-compatible cookie to survive page refresh and avoid XSS exposure via `localStorage`. Token refresh and auto-logout on 401 are handled in the Axios interceptor.

**6. TanStack Query for all server state**
No local component state for API-fetched data. Everything goes through TanStack Query's cache — this gives automatic deduplication, background refetch, and stale-while-revalidate behavior for free. Invoice polling (5-second interval during payment) uses `refetchInterval`.

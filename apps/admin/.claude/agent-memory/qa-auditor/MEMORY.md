# QA Auditor — Project Memory

> Read this before every audit; re-check the recurring findings each time. Read-only on source — report, don't rewrite.

## Definition of Done (source: system_architecture.md §9)
Per feature (before its gate) and once globally: `tsc --noEmit` + `lint` clean, no `any`, no cross-feature imports, no raw hex / off-token palette classes, no bare HTML tags in feature TSX, `tabular-nums` on numbers, both light+dark render, Figma reconciled, server-side tables with loading/empty/error states, mocks behind the service boundary, `<Can>` on privileged actions + guards in `beforeLoad`, keyboard/focus/labels/overlay containment, `logs/feature-changes/` entry present.

## Grep checks
- Tests: `npm run test` must be clean; spot-check the audited feature has colocated `*.test.tsx` covering reachability/content (pages), contract shape (services/hooks), and validation behavior (forms) — not just a trivial "renders" smoke test.
- Cross-feature: `grep -rn 'from "@/features/' src/features`
- Raw hex: `grep -rnE '#[0-9a-fA-F]{3,6}\b' src/components src/features`; palette classes: `grep -rnE '\b(slate|zinc|gray|neutral)-[0-9]' src/features src/components`
- Bare HTML in features: `grep -rnE '<(div|p|span|h[1-6]|img|a)[ >]' src/features`

Lesson: re-verify a "missing test file" claim with `find`/`git log -- <path>` before repeating it in a later audit — don't just trust the prior memory note. `integration` (2026-07-10) correctly has ZERO `<Can>` usage — it has no real mutations (row-menu items are toast stubs only), so this is the first observed correct case of a feature deliberately NOT using `<Can>` rather than a gap; verify future no-`<Can>` features similarly have no privileged/destructive action before treating absence as a finding.
- Pattern to watch on future forms: a Zod `.min(1, ...)` required-select rule can be **unreachable** if the dialog's `defaultValues` always seed from an existing entity and the `Select` offers no explicit "clear" item (unlike filter-bar selects, which commonly have an `"all"` clear value) — worth checking whether required-field validation is actually reachable through the rendered UI before treating "schema has the rule" as sufficient; `transactions`' `EditTransactionDialog` (2026-07-10) is the first observed instance of this gap.
- Pattern to watch: when money/numeric text is rendered inside a shadcn `Badge` (rather than `StatCard`'s big-number `Text` or a dedicated amount component like `CopyableAmount`), it's easy to miss `tabular-nums` on the `Badge`'s own `className` — `integration`'s `ChannelCard` balance badge (2026-07-10) is the first observed instance; grep `formatCurrency(` in new files and check the enclosing element's className for `tabular-nums` specifically, don't just grep for `tabular-nums` existing somewhere in the file.
- Shared-component *extension* (not just promotion) pattern: `StatCard` was extended in the `integration` build (2026-07-10) to add an icon+plain-caption variant alongside its original trend-pill variant, done backward-compatibly (`deltaPct`/`direction` required -> optional, only rendered together; new fields additive/optional with a defaulted `format`). Confirmed via full `npm run test` re-run that all prior consumers (dashboard/financial) still pass. Good pattern to check for on future shared-component touches: are the changed fields optional, is the old render path still reachable unconditionally, do the *other* features' existing tests still pass in the same full-suite run (not just the new feature's own tests).

## Topbar breadcrumb (`DashboardNavbar.tsx`)
Was hardcoded to the literal string `"Dashboard"` on every screen until 2026-07-10 (fixed while building `integration`, whose reference showed a leftover "Financial" breadcrumb from copying the Figma frame). Single-segment screens use a `pathname -> title` lookup (`PAGE_TITLES` const + `getPageTitle()`, mirrors the sidebar's own `useLocation`-driven active-nav pattern) keyed by exact match or `${path}/` prefix. **New protected screens must add their path to `PAGE_TITLES`** or the topbar silently falls back to "Dashboard" — note the lookup only matches real paths like `/integration`, not preview-route paths like `/integration-preview` (by design; preview routes aren't meant to drive the breadcrumb). **Exception added 2026-07-11 for `categories`:** its reference showed a real multi-segment trail ("Category › Category", "Category › Category › Add Category"), so `getCategoryBreadcrumb()` renders the installed-but-previously-unused shadcn `Breadcrumb` primitive (`components/ui/breadcrumb.tsx`) for any `/categories*` or `/categories-preview*` path (tab segment -> label via a small map + an "Add Category" trailing crumb when the path ends in `/add`), falling back to the single-title `Text` for everything else. This *is* the precedent for the next feature that needs a real nested-route breadcrumb — don't rebuild it from scratch, extend the same conditional.

## `categories` feature
Built 2026-07-11 (promoted from roadmap same day, per `product_requirements.md §4.5`) — the most complex routing of any feature so far: 5 real nested tab routes (`CategoryTabsLayout`, same URL-driven-tabs pattern as `TransactionsLayout`, but hides `TabsList` when `pathname.endsWith("/add")`) plus a genuine sub-route for the Add form.
- **Relative-nav-from-current-route pattern (new, reusable):** the "+ Add Category" button, and the Add form's Cancel/post-save navigation, all derive their target by string-manipulating `useLocation().pathname` (`` `${pathname}/add` ``, `pathname.replace(/\/add\/?$/, "")`) rather than a hardcoded absolute path — the custom `Link`/`useNavigate` wrappers accept a plain `href`/`to: string` with no route-registry typing, so this needs no casting gymnastics. This is *why* the same pages work unmodified under both the real route (`/categories/category`) and the preview route (`/categories-preview`) — use this pattern any time a page must be mountable at more than one base path.
- **First `useFieldArray` usage in the repo** (`CategoryFormFieldsBuilder.tsx`) — a dynamic repeatable-row form section (key/label/required-switch/remove per row), `Controller` for the Switch, `register` for the text inputs, empty-state message + an `Alert` info callout above the rows. Reuse this shape for any future "buyer-facing dynamic field list" builder.
- **Provisional-tab pattern:** when a spec confirms one tab's design but leaves siblings for later, build a single shared `ProvisionalTabPage(title, subcopy)` component instead of near-empty page files with duplicated JSX — each tab route is a 3-line default-export wrapper. Tabs graduate off it as their references land; only **Category Provider** is still on it as of 2026-07-28.
- **Tab names get corrected by later references — expect it.** Two of the five were renamed after the fact: "Supplier Category" → **Category Provider** (2026-07-27) and "Server Category" → **Category Server** (2026-07-28, where the reference's own tab bar disagreed with its page header, breadcrumb and buttons; page-level naming won 4-to-1). A rename means label + URL segment + page filename + barrel export + breadcrumb map + the two tab-label test arrays — grep for all four casings before declaring it done, and remember `routeTree.gen.ts` is regenerated by `npm run build`, never hand-edited.
- **One shared `DeleteConfirmDialog`** (`components/DeleteConfirmDialog.tsx`, props `{open, onOpenChange, title, description, onConfirm}`) serves every tab. Built 2026-07-27 after the same shadcn "permanently delete **your account** from our servers" boilerplate appeared in a fourth reference — it is one never-customized dialog in the source design, so never write a per-tab copy; pass wording in. Confirm label is standardized on **"Delete"**. Reversible actions get `StatusConfirmDialog` instead (neutral `Power` icon, default button variant, "you can reactivate it anytime" framing) — never the delete dialog restyled.
- **`CategoriesTable` opt-in props** accumulated across tabs: `entityLabel` (footer noun — every reference ships "of 9999999 **transactions**" copy-pasted from Transaction), `showRowNumber` ("No." column), `enableSelection` (default true; off for tabs with no bulk action). Its selection-reset effect keys on joined row ids, **not** the `data` array identity — callers pass `data?.data ?? []`, a fresh `[]` each render, which previously looped forever once a parent re-rendered on selection.
- **Trimmed server-mode table:** `CategoriesTable` copies `TransactionsTable`'s server-mode/checkbox-column/skeleton-empty-error shape but deliberately drops sortable headers and dnd-kit drag-reorder (`// ponytail:` comment on why) — not every server-mode table needs the full `TransactionsTable` feature set; trim to what the screen actually uses.
- A `CategoryStatusToggle` (Switch bound to a mutation, `<Can>`-gated with a read-only text fallback) is the precedent for an inline-editable table cell — reuse this shape over a static status `Badge` when the PRD calls for a real toggle, not just a display state.

## Testing (TDD, mandatory)
Vitest + RTL on `jsdom`, harness in `src/test/` (`setup.ts`, `test-utils.tsx`'s `renderRoute`). Test-first always: cases -> failing tests -> green. Accessible queries only, never className/token strings. Gotchas (auth-seeding, `find*` vs `get*` for query-loaded content, clipboard stub, hidden-file-input uploads, never scope by className): `topics/testing-patterns.md`. **New gotcha (2026-07-11, categories):** jsdom has no `hasPointerCapture`/`releasePointerCapture`/`scrollIntoView`, which Radix `Select` calls once a test actually opens the dropdown and clicks an `option` (not just checking the trigger's label exists) — no prior feature's tests did this. Shimmed once in `src/test/setup.ts` (`Element.prototype.hasPointerCapture ??= () => false`, etc.) — don't re-add per-test, it's global now.

## Conventions / DRY
- TS strict, no `any`. `cn()` for conditional classes, `cva` for variants. Functional components, named exports.
- **Tokens only** (no raw hex/px, no `slate-`/`zinc-`/`gray-`); monochrome; color only via `text-success`/`text-warning`/`text-destructive`/`chart-*`. Numbers use `tabular-nums`; money via `formatCurrency` (`src/utils/currency.ts`, takes an optional `{ fractionDigits }`, default 2).
- Radius `--radius: 0.375rem` (`rounded-md`); bump via `rounded-xl`/`rounded-2xl` utility overrides at the call site for a single screen's "more rounded" ask — never edit `components/ui/*` for a one-screen request (see `topics/transactions-feature.md`'s Edit dialog note).
- Reuse existing common components + the shared workhorses before writing new ones. Record new shared pieces in the relevant topic file, then add a one-line pointer here.

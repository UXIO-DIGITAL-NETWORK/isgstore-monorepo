## Latest Feature Work

### Full API Integration + Last Admin Modules (August 1 — PR #13)

The admin dashboard was built UI-first: all screens were scaffolded against typed mock fixtures behind a stable service interface, allowing the full UI to be designed and tested before the backend was ready. August 1 was the integration day — every mock service was swapped to real API calls, and the remaining sidebar modules were built and wired simultaneously.

**API groundwork (landed first):**

The swap required a coordination layer that didn't exist in the mock-only phase:
- Versioned API paths (`/v1` prefix across all endpoints, aligning with `web-topup-api` route definitions)
- Token refresh + replay interceptor — when a `401` is received, the interceptor pauses the failing request, refreshes the access token (60-minute rotation), then replays the original call. A memoization fix was applied: the in-flight refresh promise is now correctly awaited, preventing a race condition where parallel requests would each attempt their own token refresh
- Shared response mappers: `toRowId`, `toFk`, `toStatusUnion`, `unwrapPaginated` — normalizing the API envelope into the shape TanStack Table and TanStack Query expect

**Status enum alignment:**

The mock data had been using `partial_refund` and `partial_success` as transaction status values. The real API uses `pending`, `processing`, and `failed`. All status pills, filter options, and test fixtures were corrected. This also updated the DB schema on the backend side (`pending/partial_refund/partial_success` → `pending/processing/failed`).

**Last modules built and wired (same day):**
- **Content** — Banners and Announcements implemented as tabs under `/admin/content/`, mirroring the storefront's CMS consumption pattern
- **Marketing** — Promos and Flash Sales lists (Flash Sale add/edit form deferred: the master-detail editor awaited a design decision on the nesting model)
- **Administration** — Payment Channels (list + row actions), Users (read-only table; free-text balance edits belong in an audited wallet ledger, not a table field), Settings (grouped form with single bulk save, only changed keys sent to avoid unintentional overwrites)

## Key Decisions Made

**1. UI-first with mock fixtures behind a stable service boundary**
Every feature module exposes a typed service interface (`src/features/*/services/*.ts`). Mocks lived behind that interface; the real API swap touched only the service implementation, not components, hooks, or tests. This allowed 360 tests to be written against stable contracts before the backend existed.

**2. TDD-first, no exceptions**
The workflow is test cases → failing tests → implementation to green. This is enforced by the project's `.claude/rules/` — no screen or component is considered done until tests are written first. This caught the status enum mismatch immediately when real API responses arrived with unexpected values.

**3. Users table is read-only**
The API has full CRUD on users, but balance editing is intentionally omitted from the table. Balance mutations belong in an audited wallet ledger with a full audit trail, not a free-text field in a data table where changes are invisible.

**4. Settings: single bulk save, touched-keys only**
The Settings screen sends only the keys whose values changed, not the full settings object. This prevents accidental overwrites of settings that aren't visible on screen, and avoids Zustand effect-seeding lint errors that arise from mirroring server state to local state.

**5. Sub Category clears on parent Category change**
When the user changes the Category in a product or sub-category form, the Sub Category field auto-clears and refetches only that category's children. Stale sub-category selections from a previous parent are rejected at the form schema level (Zod).

**6. Flash Sale add/edit deferred**
The Flash Sale list and API service exist, but the add/edit form is deferred. The nesting model (Flash Sale → SKU lines → tier pricing) requires a master-detail editor pattern that wasn't specced in time to ship with the rest of Marketing. Listed as known pending work.

**7. shadcn/ui neutral palette (true monochrome)**
The admin SPA uses shadcn in `new-york` style with a true-neutral base — no blue tint. Tokens are defined in `src/index.css` via Tailwind v4 `@theme`. Light + dark modes both verified for every new screen.
